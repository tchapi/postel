# Spike: contacts from Davis over CardDAV

Date: 2026-10-23. Setup: `dev/davis` (davis-standalone 5.5.1 on SQLite), user
`alice` with one address book of 300 synthetic contacts from
`dev/davis/seed.sh`. Loopback on a laptop, so absolute numbers are optimistic.

## Questions

1. Is CardDAV enough for autocomplete, or does Davis need a new API?
2. What does a query cost, and how do we keep a cache fresh?
3. How does the webmail authenticate against Davis without the user's password?

## Findings

### CardDAV is the API

Everything autocomplete needs is standard sabre/dav behaviour, no Davis
change required:

| Request | Time | Notes |
| --- | --- | --- |
| `PROPFIND` on the address book for `getctag` + `sync-token` | 168 ms | 466 bytes, the cheap "did anything change" poll |
| `REPORT addressbook-query`, `text-match contains` on `FN` or `EMAIL` | 170 to 177 ms | case-insensitive with `i;unicode-casemap`, `test="anyof"` for FN or EMAIL |
| `REPORT addressbook-query`, no filter, `FN` + `EMAIL` only | 188 ms | 126 KB for 300 cards, the full cache refresh |
| `REPORT sync-collection` with a known token | 174 ms | returns only the cards changed since, 1 href after a `PUT` |

Wrong password gets a 401, another user's address book a 404, as expected.

### Every request costs ~170 ms, whatever it does

The time is flat across requests, so it is not the query. It is Basic auth:
Davis verifies a bcrypt hash on every request, and `password_verify` alone
measured 170 ms in that container (an unauthenticated request is 3 ms).
Hitting CardDAV per keystroke is out, which is what we expected anyway.

Design, unchanged from the plan: the webmail keeps `name` + `email` for each
contact in its SQLite file, refreshes with `sync-collection` when the
`sync-token` moved (one cheap `PROPFIND` to know, at most every few minutes),
and autocomplete is a `LIKE` on the cache.

### Authentication: Davis needs a master user

The webmail knows the user from the forward-auth headers, not their Davis
password. Davis has an API token (`X-Davis-API-Token`) but the API only lists
users, and a token that reads every address book is more power than needed.

Proposal for Davis, mirroring the Dovecot trick we already rely on: in
`App\Services\AbstractAuth::validateUserPass`, when the username is
`<login>*<master>` and `<master>` plus the password match two new env vars
(`MASTER_USER`, `MASTER_PASSWORD`), authenticate as `<login>` through
`setCanonicalUsername()`. It sits above the Basic, IMAP and LDAP backends, so
it works for all of them, and `breaksPrincipalUri()` still applies to the
login part. A few dozen lines plus tests.

Until it lands, a per-user Davis password stored encrypted in the webmail
settings would work too. Not keen, but it unblocks phase 3.

## Decisions

- No new API on Davis: `addressbook-query` for the first fill,
  `sync-collection` for refreshes, `getctag`/`sync-token` to know when.
- Contacts cache in the webmail's SQLite, autocomplete never touches Davis.
- Open a PR on Davis for the master user before phase 3. It became app keys
  instead, scoped per user and revocable:
  [tchapi/davis#313](https://github.com/tchapi/davis/pull/313).
- Davis username is the forward-auth `Remote-User` (`alice`), not the email.
  Configurable later if someone's Davis logins are emails.
